# @cningan/dsh-session-status

English | [中文](README.zh.md)

Canonical behavior, invariants, and spec: [SPEC.md](SPEC.md).

## What it does

This DSH Web Client plugin sends attention reminders for **every observed running session**, including sessions not currently selected. It distinguishes a wait for approval, plan review, or a question from a completed, interrupted, failed, or otherwise unclassified stop. A stop with insufficient cause data is reported generically rather than mislabeled as successful completion. An observed turn explicitly attributed to user cancellation is silent. An explicitly removed selected session is silent when that detail is available; a missing list row suppresses its terminal edge to avoid removal/archive notices. Background removal detail is not read. It does not draw reminder cards or a status overlay inside the page; a global DSH connection loss is not treated as a session stop.

Reminders are emitted only when the corresponding DSH page/window is hidden or unfocused; selection of a session does not limit which running sessions are watched. Clicking a browser notification asks DSH to open its session and focuses the window; native-bridge click handling belongs to the external workbench and is not verified here. There is **no settings UI and no foreground exception**: every reminder — including the test-service probe used by the in-repo `dev/` panel — obeys the same foreground veto. Browser notification permission is requested automatically the first time a reminder actually needs to be delivered while the permission is still undecided (`default`); there is no button to press.

The plugin uses the official session list and all-session status map, plus the selected session's `SessionSnapshot` and `eventSource` when available. An unread-completion marker alone neither triggers a notice nor proves success; only an observed running-to-stopped edge is actionable, and absent `turn/end` cause data stays generic. Other sessions are never opened just to obtain detail or event history. Connection state is used only to re-sync after reconnection. DSH remains the owner of session truth and recovery. The plugin keeps only ephemeral edge-deduplication and delivery-capability state; it does not persist session state or serialize whole session objects.

## Delivery paths

- In the DSH workbench, the channels are an **ordered adapter sequence**: `window.dshShell.notify(payload)`, then `window.chrome.webview.postMessage(payload)`, then the browser `Notification` API. Each channel declares whether it can deliver right now and what its delivery did (accepted / rejected / unavailable); the two bridges are fallback channels (a throw is recorded and the sequence moves on), and the browser is the terminal channel that owns the wording for "no channel" (`browser-<permission>` / `browser-unsupported`) and for a terminal refusal (`browser-error`). Which channels are available right now has a **single source** (`readCapabilities`): the delivery decision, the delivery result, the reported record and the permission question all consume the same value instead of re-deriving it, and a bridge being present is a shape *claim* while a throw is what disproves it. The checked Desktop bundle exposes no plugin-callable flash-only API; its `flashFrame` calls are private to modal UI. The inspected preload exposes `dshDesktop`, but no notification method was found; availability of the optional `dshShell`/WebView notification bridges in a target runtime is unverified. A flash-only route would require a DSH core/preload change, which the user declined, so this plugin keeps its existing bridge path and falls back to browser notifications if no bridge is exposed or all exposed bridges throw. A silent no-op from an exposed bridge cannot be detected.
- If neither workbench bridge succeeds, it falls back to the browser Notification API when browser permission is granted; in a direct browser, that is the primary path.
- Browser notifications set `silent: false` to request platform sound and always use a unique `tag`; they deliberately **never set `requireInteraction`**. In the desktop WebView a notification with `requireInteraction: true` is silently dropped — the constructor succeeds, but the platform never shows it and fires no `onshow`/`onerror`/`onclose` (confirmed by an A/B probe on 2026-09-26). All reminders therefore expire on the platform's default timeout. The native bridge payload has no sound field, so its sound behavior belongs to the external workbench. Browser/WebView and Windows settings remain authoritative; this plugin cannot override mute, Focus Assist, or volume settings.

The shell implementation is an external integration boundary and is not included in this repository.

## Package entry points

- The package name is @cningan/dsh-session-status, version 0.5.0. It is published to the npm registry under that name (`publishConfig.access: public`) and declares `engines.dsh`.
- lib/index.js is the Host half: it injects `webServer`, owns the diagnostics sink (`/plugins/dsh-session-status/diagnostics`), and appends JSONL records under the profile's `.dsh-session-status/` directory. It never decides when a reminder is due.
- lib/client.js is the loader-ready Client bundle: it registers the session notification capability and the test service `sessionStatusTest` (`ctx.provide`). It ships **no settings UI at all** — no slot, no stylesheet, no React — and its Client dependency list therefore has no `slots` (`locale` stays: it serves the reminder copy).

The package declares `dsh.bundle.patch` (`cordis.patch.yml`), so the official channel can treat it as a bundle: install it with `plugin_manager` `install_bundle` (or Add plugin in the client) and that patch mounts the package's own entry (`id: session-status`, `name: '@cningan/dsh-session-status'`). Install it from the **npm registry by name** — that is the only form the DSH Plugins page can check for updates and upgrade in place (a local `.tgz`, a GitHub link or a `github:` spec is reported as not updatable, so it can only be removed and reinstalled). A local `.tgz` still works for offline verification; do not use a directory or `link:` input, which only creates a junction and cannot resolve `@deepseek-ai/*`.

`engines.dsh` is `>=0.2.0 <0.3.0`: DSH validates it on install and again at startup with `semver.satisfies(runtime, range, { includePrerelease: true })`, and refuses an unmet requirement with `incompatible-version` (a profile can grant an exemption in its own `compatibility.json`). The guard is deliberate — 0.3.1 loaded silently and then misbehaved on 0.2.2, so a loud refusal is better than a quiet one.

This repository is the maintained source location. A deployed profile is an external runtime/composition target; this repository does not hand-edit profile files (no manual `package.json` or `dsh.profile.bundles` changes).

## Permission and checks

The plugin has **no settings page section**; there is nothing to configure for reminders. It ships a **debug panel inside its own plugin page** (Plugins → this plugin → detail page) that is **off by default**: while the master switch is off the service rejects every test action, so normal use is unaffected. Once enabled it can force foreground/background (a **global** override: with it, a real session stop pops even though the page is in the foreground) and simulate a reminder for each of the 11 stop reasons. Reminder text follows the DSH interface language through the official locale service. Browser notification permission is requested automatically when the first reminder actually needs to be delivered and the permission is still undecided (`default`): the request is asynchronous, so that first reminder is still recorded as "no channel" (`browser-default`) and later reminders take the browser channel once the permission is answered. If a native workbench bridge is present, the browser permission is never needed. To exercise the delivery path on demand, use the separate in-repo debug panel (`dev/debug-panel/`), whose probe (`deliverAdHoc`) shares the delivery instance, the key counter, the diagnostics and the foreground veto with automatic reminders.

The `desktop` profile has the plugin installed through the official channel from a local tarball. The automatic session-stop path still requires an end-to-end check in a separate DSH session; do not treat the test-service probe or unit tests as that validation.

## Diagnostics

The Client half reports what it observed — load snapshot, session/status source shape, run edges, the foreground test, the delivery result, and the platform's own notification lifecycle events — to the Host half, which appends them to `<profile>/.dsh-session-status/diagnostics.jsonl`; the Host also writes a `host-ready` marker on load, which separates "Host never ran" from "Client never reported". The event vocabulary, each event's minimal payload shape, and the record envelope have a **single owner** that the Client sender, the Host and this reader all consume; the Host is the **gate**: it validates before appending, so a report whose shape does not match is refused instead of silently written — the request gets a 400 carrying the running refusal count, and a `diagnostics-rejected` fact is appended to the same JSONL. Every Client record also states which build produced it (`build`); the bundle is minified and, since test capability moved out, it is the only observing instrument (records say `production`; `debug` stays a value the reader understands for older records), and Host-written lines say `host`. The contract only ever gains fields: existing fields and values stay byte-identical, unknown fields and a missing `build` (an older Client) are tolerated, so Host and Client can be upgraded independently. The reader therefore tolerates unknown fields and **only interprets the events it knows** (a Host line or an unrecognized name only shows up in the event histogram). Run `npm run diagnose` (or `node scripts/check-diagnostics.mjs <file>`) to read that file and get a verdict with an exit code. The verdict words and their exit-code meanings have a **single source of truth: the `VERDICTS` table documented at the top of `scripts/check-diagnostics.mjs`** — this document deliberately does not restate them. The reader separates "the delivery call succeeded" (`delivered: true`, i.e. `new Notification()` did not throw) from "the platform confirmed the notice was shown" (an `onshow` or `onclose` for the same key): only the latter is the evidence [ADR-0001](docs/adr/0001-no-require-interaction-short-unique-tags.md) rests on. A successful call with no platform event for that key is reported as unconfirmed, never as success, and an `onerror` is reported as a platform rejection carrying its error text. This is how a run is audited after the fact instead of watching the window.

## Compatibility

This bundle consumes `uiSession.sessionStatus`, `connection.state`, the selected binding's `eventSource`, official `SessionSnapshot` error fields, and — for opening a session from a notification — the optional official `uiWorkspace` service. It does not depend on undocumented `nodes`. It accepts **both** session event-window shapes: `{ entries, hasMore, revision, change }` (DSH 0.2+, entries are `{ type, event }`) and the older `{ events, target }`; `turn/end` reasons are classified from whichever shape arrives, and a shape that matches neither degrades to a generic notice plus one `source-shape` record. See [docs/compatibility.md](docs/compatibility.md) for the verified 0.2.2 contract details.

## Build

`lib/client.js` is a **build artifact** (esbuild bundle, header marks it "do not edit") generated from `lib/client/`:

There is a **single build**. Test capability does not live in this plugin ([ADR-0003](docs/adr/0003-test-capability-lives-outside-the-plugin.md)):

- `npm run build:client` — the only bundle: it carries no test UI and no settings UI, but it does register the test service `sessionStatusTest` (`ctx.provide`), the hook the separate `dev/` debug plugin injects
- `npm test` — its `pretest` builds that bundle first; the suite then runs against it
- `npm run check:production` — builds and asserts the artifact's surface: removed debug/settings capabilities never come back, the expected hooks are present, and the debug switch starts **off**; no settings UI (no `dshss-settings` class, no `settings.section` registration), and the test-service hook present (a positive control)
- `npm run diagnose` — reads `<profile>/.dsh-session-status/diagnostics.jsonl` and prints a verdict with an exit code; it consumes the same diagnostics contract as the sender and the Host gate, and only interprets the events it knows
- `prepack` builds the same bundle, so tarball installs never ship test code

## Build and test status

Run `npm test` for the built-in Node test suite covering session edges, terminal reasons, channel detection, foreground rules, connection-loss suppression, locale-dictionary language following, the **automatic permission request** (undecided permission is asked for exactly once, at the first reminder that actually needs delivering, and only from a non-UI path), the normalization layer (title fallback, error-detail extraction, list/status shaping, and the four foreground cases: hidden / unfocused / visible-and-focused / no host page, plus a single-source guard that only the normalization module may read page visibility or focus), the delivery layer's channel fallback and platform-event feedback (minimal doubles only, no whole-browser simulation; each channel is an independently testable adapter whose availability and three outcomes can be asserted from a capability value alone), the **test service** (the three foreground-override states and their effect on delivery suppression — verifiable in both directions — the mode gate, `deliverAdHoc` sharing the delivery path and the key counter with automatic reminders while still obeying foreground suppression, subscribe/unsubscribe, and the override being visible in what gets reported), the **artifact surface** (the service registered through `ctx.provide` with exactly its four contract methods and no internal collaborator leaking, plus no debug traces and *no settings UI at all* — no settings class name and no slot registration — while the hook markers are present as a positive control), the diagnostics reader's verdicts (fixed-sample JSONL for platform-confirmed, platform-rejected, and unconfirmed deliveries), the **diagnostics contract** (the vocabulary, the write-side prefix rule, the payload-shape table's own well-formedness, every point-mutation of a valid record being refused, forward-compatible unknown fields, the envelope field order, the reader interpreting only the events it knows, honest build labeling, and the real bundle's every reported record passing the same validator), and the **capability single source** (one derivation per delivery, the permission question and the per-channel availability coming from that same value, plus a source guard that only the delivery module may read `navigator.userActivation` / the `Notification` global / the `dshShell` and `chrome.webview` bridges). Judgment assertions live in those direct Node tests; the whole-browser `vm` harness is limited to seven assembly-level integration tests (subscription → decision → wording → delivery → reporting) that assert only what is observable through the full assembly. The checked-in Client file is already the DSH loader bundle; tests do not replace host/plugin integration or real notification testing.

## Known limitations

- There is no settings UI: browser notification permission can only be requested automatically, at the first reminder that needs delivering. That first reminder is still recorded as undelivered (`browser-default`) while the request is pending, and if the permission is denied it cannot be re-requested from inside the plugin.
- Browser notification permission and sound are controlled by the browser/WebView and operating system.
- Workbench bridge availability and presentation are unverified in a live target; the inspected Desktop preload exposed no notification method.
- If no current-session `turn/end` reason or explicit error is available at the stop edge, the plugin uses a generic unknown-stop notice. Removed state is read only for the selected session; background Stop/Cancel/removal attribution may therefore be unknown and notify generically. A missing list row at the stop edge is suppressed as a possible archive/removal.
- Durable session truth and connection recovery remain owned by DSH.
